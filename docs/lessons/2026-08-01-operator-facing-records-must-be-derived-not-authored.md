# Lesson — Operator-facing records must be DERIVED, not authored

**Date:** 2026-08-01
**Trigger:** Operator, on being handed a list of bare labels to action: *"you're giving me next to
no context for each of the bulleted items that you're asking me to do. I don't know what exactly it
is that you want me to do for these."* Then, on being told the canonical ledger was stale and
unreadable: *"Why is the documentation for me unreadable and stale? What do we need to change in
the deterministic harness to make this always useful and always current?"*

The second question is the right one. This is the structural answer.

## The observation that makes this a class, not an incident

In ONE session (Circuit, 2026-07-31 → 08-01), four independent hand-maintained records were found
drifted from reality, all in the same direction — **claiming less-done than truth, or claiming
work that was already finished:**

1. **Phase 4 plan checkboxes** — 31 of 33 shipped tasks still showed `[ ]`. Seventeen were
   confirmed shipped-but-unchecked in a single audit; one had shipped in a PR **three months before
   the plan was written**. Two full builder dispatches were spent discovering their assigned task
   was already done. The plan also claimed 60 tasks; it contains 55.
2. **`NEEDS-YOU.md`** (the canonical awaiting-operator ledger, machine-generated by
   `~/.claude/scripts/needs-you.sh`) — last generated 2026-07-28, entries dating to 2026-07-08 still
   listed as open, each a single ~900-character undelimited paragraph with the title line and body
   line byte-identical, bundling three unrelated asks into one entry.
3. **`ENVIRONMENTS.md` §"Current gaps"** — listed two mechanisms as "not built yet" that
   demonstrably existed on disk.
4. **`docs/PRIORITIES.md`** — asserted a plan "does not exist yet and no PR references it
   (verified against GitHub and all local branches)". The plan was a 53KB file merged two days prior.

Four files. Four authors. One failure mode.

## The root cause

**Every one of these is a hand-maintained CLAIM about state that has a machine-checkable ground
truth sitting right next to it.**

- "Is this task shipped?" → answerable by grepping the repo at HEAD.
- "Is this PR still blocking?" → answerable from the GitHub API.
- "Does this secret exist?" → answerable from the repo settings API.
- "Is this migration applied?" → answerable from `supabase_migrations.schema_migrations`.
- "Does this file exist?" → answerable by looking.

The records went stale because they are **logs of things once said** rather than **projections of
things now true**. A log has no mechanism that notices when its contents stop matching the world;
it can only be corrected by someone remembering to correct it, which is precisely the reliance the
harness exists to eliminate.

The proof that derivation works: the same session ran a reconciliation agent whose entire method
was "query the repo for each claim." It produced a different — and correct — answer than the
checkboxes had held for weeks, in one pass.

## Compounding factor: append-only with no closing predicate

`NEEDS-YOU.md` can add entries. Nothing can remove one, because nothing knows when an item is
done. Creating an operator-ask is frictionless; closing it is voluntary. This is the same asymmetry
named in [`2026-07-27-outcome-blind-closure-and-estate-entropy.md`](2026-07-27-outcome-blind-closure-and-estate-entropy.md)
root cause #2 — *"Creating autonomous work is frictionless; closing it is voluntary. Entropy wins
by default"* — recurring in a different surface. That lesson predicted this one.

## The four proposed changes

Ordered by leverage. **A is the load-bearing one**; B–D are what you do for the residue A can't cover.

### A. Make the ledger a VIEW, not a LOG (the actual fix)

A generator that queries GitHub, Supabase, the repo, and provider APIs, and renders current truth
on every invocation. It **cannot go stale, because there is nothing to remember to update.**

Most real operator-asks are already derivable:
- blocked PR → `gh pr list` + `mergeStateStatus`
- missing/dead secret → repo secrets API + last successful workflow run
- unapplied migration → `supabase migration list`
- un-backfilled org field → a DB query
- flag awaiting promotion → a column read

**Justification:** this is the only one of the four that removes the failure mode rather than
patrolling it. B, C, and D all still depend on an agent doing something correctly at capture time.
A depends on nothing but the query being right, and a wrong query fails loudly rather than silently
aging.

**Refuter (state it, per constitution §1):** if most asks turn out NOT to be mechanically derivable
in practice, A degrades to a small view plus a large hand-authored remainder, and B/C/D carry the
weight. Test before building: take the current open asks and count how many have a machine-checkable
predicate. In the Circuit instance, **five of six did.**

### B. Every non-derivable entry carries a resolution predicate

For the residue A can't derive, require a machine-checkable "how would I know this is done" at
capture time — `pr:1203 merged`, `secret:PROJECT_TOKEN valid`, `org:X.brand_sid not null`. The
renderer auto-closes any entry whose predicate is satisfied.

**Justification:** converts append-only into self-cleaning. Without this, A fixes the derivable
items and the hand-authored ones keep accumulating exactly as they do today.

### C. Schema at the capture gate, enforced by refusal

Require named fields — `blocked`, `why`, `exact_action`, `unblocks`, `evidence_link` — and **refuse
to write** an entry missing any. Today a bad entry is discouraged; it should be impossible.

**Justification:** this is the Mechanism-vs-Pattern distinction the harness already draws. The
current script accepts free text and echoes it, so output quality equals whatever an agent happened
to type — reliance on discipline, which is the thing being engineered away. Note the operator's
complaint was about CONTENT quality ("I don't know what exactly you want me to do"), and C is the
only change that addresses content rather than freshness.

**Cost, named honestly:** a refusing gate has a false-positive rate. An agent with a legitimate ask
that doesn't fit the schema will either mangle it to fit or skip filing. Mitigate with an explicit
`freeform` escape that is visibly marked as lower-quality, not by loosening the schema.

### D. Staleness fails loudly

If the ledger's generated-at is older than N days while open items exist, session-start says so —
same posture as the doctor.

**Justification:** cheapest of the four, and it is the backstop for A's failure. If the generator
breaks, the file freezes at its last good render and looks perfectly healthy — exactly how a
*cancelled* GitHub job looked green in the same session, and how a dead email channel carried a
correctly-fired CRITICAL alert to nobody. **Silence must never be a possible success signal.**

## The generalizable rule

> **If a fact about state can be queried, never store a human's assertion of it.**
> Store the query. Render the answer.

Applies well beyond this ledger: plan checkboxes, "current gaps" sections, priorities boards,
readiness matrices, and every doc section beginning "as of <date>". Each is a cache with no
invalidation, and a cache with no invalidation is a future lie with a timestamp on it.

## Scope note

The generator is `~/.claude/scripts/needs-you.sh`, machine-wide — it affects every project on the
box, not only the one where the failure was observed. Per `CLAUDE.md`, harness changes are made in
the harness repo and land via `install.sh`; `~/.claude/` is never hand-edited. **A–D are proposals
recorded here, not shipped**, pending operator go-ahead on scope and timing.
